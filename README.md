# recurring-task-reminders

Напоминания о повторяющихся регламентных задачах компаний (например, «продлить SSL-сертификат раз
в 90 дней»). Каждый день в 09:00 по Алматы Celery beat запускает рассылку, и каждый ответственный
получает **одно** письмо-дайджест со списком задач, у которых срок в ближайшие 3 дня или уже прошёл.

Стек: Python 3.12, Django 5.2, Celery 5 + beat, Redis, PostgreSQL 16, pytest-django, time-machine, HTMX.

## Быстрый старт

```bash
cp .env.example .env            # или: make env
docker compose up --build -d    # web, db, redis, celery, beat
docker compose exec web python manage.py seed_demo
docker compose exec web python manage.py send_digests   # письма печатаются в вывод команды
docker compose exec web python manage.py send_digests   # второй раз: «Отправлено писем: 0»
```

* Админка: http://localhost:8000/admin/ (логин и пароль `admin` / `admin` из `.env`; суперюзер
  создаётся автоматически при старте `web`).
* Страница «Ближайшие сроки»: http://localhost:8000/upcoming/ (только для staff).
* Где смотреть письма. `EMAIL_BACKEND = console`, поэтому письмо печатается в stdout того процесса,
  который его отправил:
  * по расписанию (beat → worker): `docker compose logs celery`;
  * через Celery вручную: `docker compose exec web python manage.py send_digests --async`, затем
    `docker compose logs celery`;
  * `send_digests` без флага выполняется прямо в команде, письма видно в её выводе.

Остановить: `docker compose down` (с `-v` удалится и база).

## Модель данных

| Модель | Поля | Примечания |
|---|---|---|
| `Company` | `name` (unique), `created_at` | |
| `Task` | `company` → Company, `title`, `responsible_email`, `cycle_days` (≥ 1), `last_done_at` (date, null), `status` (`active`/`paused`), `created_at` | `cycle_days ≥ 1` проверяется валидатором (формы) и `CheckConstraint` (БД) |
| `ReminderLog` | `email`, `sent_on` (date), `task_ids` (JSON), `created_at` | `UniqueConstraint(email, sent_on)` — защита от дублей |

## Правила расчёта сроков

«Сегодня» везде считается как `timezone.localdate()` в зоне `Asia/Almaty` (`USE_TZ = True`,
в БД время хранится в UTC).

* **`next_due_date`** = `last_done_at + cycle_days`.
* **Если `last_done_at` пустой** (задача ни разу не выполнялась), срок равен **дате создания задачи
  по Алматы**. Логика такая: раз задача заведена, но не выполнена, о ней нужно напомнить сразу.
  Пока задачу не отметят, она остаётся в дайджесте как просроченная. Дата берётся локальная: задача,
  созданная 10.06 в 02:00 по Алматы (это 09.06 в UTC), получает срок 10.06.
* **`is_due(days_ahead, today)`** = задача активна **и** `next_due_date <= today + days_ahead`.
  Окно включительное, просроченные тоже попадают.
* **`mark_done(on)`** ставит `last_done_at = on` (по умолчанию сегодня), поэтому следующий срок
  считается от фактической даты выполнения, а не от старого срока.

Примеры при `today = 10.06`, `days_ahead = 3`:

| Срок | Попадёт? | Пометка в письме |
|---|---|---|
| 05.06 | да | ПРОСРОЧЕНО на 5 дн. |
| 10.06 | да | сегодня |
| 13.06 | да (граница окна) | через 3 дн. |
| 14.06 | нет | — |
| любой, статус `paused` | нет | — |

Календарные границы: `28.02.2028 + 1 = 29.02.2028` (високосный год), `28.02.2027 + 1 = 01.03.2027`,
`31.01.2028 + 30 = 01.03.2028`, `31.12.2026 + 1 = 01.01.2027`.

### Один и тот же расчёт в Python и в БД

Для рассылки задачи не перебираются в Python. `TaskQuerySet.due()` считает срок прямо в SQL:

```sql
COALESCE(last_done_at + cycle_days, (created_at AT TIME ZONE 'Asia/Almaty')::date) <= :deadline
```

В PostgreSQL `date + integer` даёт `date`, а `TruncDate` в Django учитывает `TIME_ZONE`.
Тест `test_queryset_due_matches_is_due` проверяет, что `due()` и `is_due()` выбирают одинаковые
задачи на наборе граничных случаев (включая 29 февраля и переход года).

## Защита от дублей писем

Для каждого ответственного (`services.send_digest`):

```python
with transaction.atomic():
    log, created = ReminderLog.objects.get_or_create(email=email, sent_on=today, ...)
    if not created:
        return False          # сегодня этому адресу уже отправляли
    send_mail(...)
```

**Почему это работает даже при двух параллельных запусках.** Решение принимает не Python-код, а
уникальный индекс в PostgreSQL по `(email, sent_on)`:

1. Запуск A вставляет строку `(ops@…, 10.06)`. Транзакция A ещё не завершена.
2. Запуск B не находит строку (A ещё не закоммитил) и пытается вставить такую же. PostgreSQL видит
   конфликт по уникальному индексу и **заставляет B ждать**, пока A завершится.
3. A отправляет письмо и коммитит. Вставка B падает с `IntegrityError`. `get_or_create` ловит
   ошибку, перечитывает строку и возвращает `created=False`, поэтому B письмо не отправляет.
4. Если у A упал `send_mail`, транзакция откатывается вместе со строкой журнала. Тогда вставка B
   проходит, и B отправляет письмо сам. Следующий запуск тоже повторит попытку.

Проверка «есть ли запись» через обычный `SELECT` без уникального индекса так не работает: оба
запуска увидят «записи нет», и оба отправят письмо.

**Компромисс.** Письмо уходит внутри транзакции. Если SMTP принял письмо, а коммит после этого
упал (большая редкость), письмо может уйти повторно на следующем запуске (at-least-once). Если
нужна строгость «не больше одного письма», журнал можно коммитить до отправки (at-most-once), но
тогда при сбое SMTP письмо потеряется. Для напоминаний лучше лишнее письмо, чем пропущенное.

## Celery и расписание

* `config/celery.py` — приложение Celery, настройки берутся из `settings.py` с префиксом `CELERY_`.
* `CELERY_BEAT_SCHEDULE` в `settings.py`: задача `reminders.tasks.send_due_digests` каждый день
  `crontab(hour=9, minute=0)`. Зона расписания: `CELERY_TIMEZONE = "Asia/Almaty"`.
* `send_due_digests(days_ahead=3)` возвращает число отправленных писем. Вся логика лежит в
  `reminders/services.py`, задача Celery только её вызывает.

## Admin

* **Компании** — с inline-списком задач.
* **Задачи** — колонки: компания, название, ответственный, цикл, дата выполнения, следующий срок
  (с сортировкой, считается в БД), цветная пометка (красная — просрочено, оранжевая — ≤ 3 дн.,
  зелёная — ок, серая — пауза). Есть фильтры по статусу и компании и поиск.
* Действие **«Отметить выполненным (сегодня)»** для выбранных задач и такая же кнопка на странице
  задачи.
* **Отправленные дайджесты** (`ReminderLog`) — журнал отправок.

## Бонус: страница «Ближайшие сроки» (HTMX)

`/upcoming/` (только staff). Выпадающий список 3/7/30 дней делает `hx-get` и перерисовывает
только `<tbody>`: сервер видит заголовок `HX-Request` и отдаёт фрагмент `_rows.html`. Кнопка
«Выполнено» делает `hx-post /upcoming/<id>/done/` и заменяет строку ответом (`_row.html`) с новым
сроком. CSRF-токен передаётся через `hx-headers` на `<body>`. Стили — Pico.css из CDN.

## Тесты

```bash
make test                          # = docker compose run --rm web pytest
make lint                          # ruff check + ruff format --check
```

Тесты идут на PostgreSQL из compose (как в проде, ведь арифметика дат в SQL зависит от СУБД).
Время фиксируется через `time-machine`: по умолчанию «сейчас» = 10.06.2026 10:00 по Алматы.

* `test_models.py` — `is_due`/`next_due_date` на границах окна, просрочка, пустой `last_done_at`
  (с проверкой часового пояса), пауза, `mark_done`, конец месяца/года, 29 февраля, ограничение
  `cycle_days ≥ 1`, совпадение `due()` и `is_due()`.
* `test_tasks.py` — одно письмо на ответственного, сортировка и пометки, окно и пауза, повторный
  запуск даёт 0, на следующий день письмо уходит снова, после `mark_done` задача пропадает, при сбое
  отправки журнал откатывается.
* `test_admin.py` — action, кнопка на странице задачи, пометки и сортировка в списке, inline.
* `test_views.py` — логин и staff обязательны, фрагмент для HTMX, фильтр по дням, «Выполнено».

## Структура

```

reminders/
  models.py        Company, Task, ReminderLog

  tests/
```
